# Kanjo and ISO/IEC 27001:2022

## What this document is and is not

A tool cannot be certified against ISO/IEC 27001. What is certified is an organisation's information security management system (ISMS): its scope, its risk assessment, its Statement of Applicability, and the evidence that the controls it chose are in place and work. This document does not say that Kanjo is "compliant", and using Kanjo does not satisfy any control by itself.

What it does is map Kanjo's design to the controls of Annex A of the 2022 edition that genuinely apply to a tool of this kind. For each control it says how Kanjo supports it, where a reviewer can find the evidence in this repository, and what remains the organisation's job. Controls that Kanjo has nothing to do with (physical security, human resources, supplier contracts and most organisational controls) are left out rather than listed with an empty answer. Control titles follow the 2022 edition as published in secondary sources, since the standard itself is not freely available; check them against your copy.

Kanjo is an offline cost and limit monitor for Claude Code: one binary that a developer runs on their own computer, which reads Claude Code's local files and shows cost, token use and subscription limits in a local dashboard. It is an independent open-source project published by Kyotu under the Apache License 2.0 and is not made, endorsed or supported by Anthropic. "Claude" and "Claude Code" are Anthropic's names for its products. This release is a single-user tool: there is no team server, no user accounts and no central collection of data.

Some evidence below has a limit that matters for an audit, and it is stated where it applies. In particular: the macOS and Windows release builds exist only as CI definitions and have never been run; the release workflow, including signing, has never been executed; the CI jobs named as evidence are defined in `.github/workflows/` but this document does not claim that they have passed; and the repository address `https://github.com/kyotu/kanjo` used in `SECURITY.md`, the installers and the signature identity is an assumption until the repository is published.

Two companion documents carry most of the detail: [data-inventory.md](data-inventory.md) lists every kind of data Kanjo stores or reads, and [threat-model.md](threat-model.md) lists the threats considered, the mitigations and the residual risk.

## A note on classification and the confidence labels

Every number in Kanjo's dashboard carries a label: official, estimate or lower bound (`Confidence` in `crates/kanjo-core/src/api.rs`). These labels say how far a figure can be trusted (whether Claude Code reported it, Kanjo derived it, or it was summed from transcripts that may miss requests). They are not an information classification and must not be presented as one for A.5.12 or A.5.13. Kanjo has no classification scheme of its own; the data inventory groups its data by kind and says which kinds can identify a person or a client, which is the input an organisation needs to classify it under its own scheme.

## Operator checklist

A company that adopts Kanjo should decide and record the following, in its own ISMS documents rather than in Kanjo.

1. **Asset register entry.** Kanjo, its version, who installed it on which machines, the data directory, where the database key is (keyring or `kanjo.key`), where backups and exports go, and the owner of each installation (normally the developer).
2. **Configuration standard.** Loopback only or not; `auth = "token"` everywhere; the encryption mode, and whether the key-file fallback is acceptable; whether path redaction is required, and when.
3. **Transcript viewer.** Who may switch it on. The simplest rule is that only the developer who owns the installation may, only on their own machine, and that it stays off on any installation someone else can reach. Review `settings.update` and `transcript.view` entries in the audit log if this matters.
4. **Retention periods.** Requests, hourly aggregates, limit readings, alerts, audit log and quarantine, set in Settings -> Retention, and how long exported files and backups may be kept, since Kanjo's retention does not reach them.
5. **Key and database backup.** Whether the data is worth backing up; if so, how often, where the copies go, and how the key is kept separately from them. A backup without its key cannot be restored.
6. **When a developer leaves or a device is reassigned.** Decide whether the data is kept (make a backup and keep the key) or deleted. To delete: run `kanjo uninstall --purge-data` (it removes Kanjo from Claude Code, stops the service and deletes the data directory), remove the `kanjo` entry from the OS keyring, delete the `settings.json.kanjo-backup-*` files next to Claude Code's `settings.json`, and delete any backups or exports copied elsewhere. Reimaging the device covers all of it. If the installation was ever reachable by others, its token dies with the data directory.
7. **How to verify a release.** Check the archive against `SHA256SUMS`, check `SHA256SUMS` with `cosign verify-blob` against the release workflow identity for that tag, and optionally check the provenance with `gh attestation verify` and the embedded dependency list with `cargo audit bin`, as described in [release.md](../release.md). Install with cosign available so that the installers verify the signature themselves, do not use `--skip-signature` unless the machine cannot reach Sigstore, and never use `--no-verify`, which installs an offline archive without checking it. Until the first release has been published and verified this way, treat the procedure as untested.
