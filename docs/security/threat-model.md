# Threat model

This is a short threat model for Kanjo as it is in this repository: a single `kanjo` binary that one person runs on their own computer to see the cost and limits of their Claude Code sessions. It says what Kanjo protects, which boundaries it defends, which threats were considered, how each is mitigated and what risk remains. It was written from the code (chiefly `crates/kanjo-server/src/security.rs` and `net.rs`, `crates/kanjo-ops/src/keys.rs` and `token.rs`, `crates/kanjo-setup/src/server_file.rs`) and from the security findings of an internal review and the fixes made for them. It covers one user on one machine; there is no team or company server.

Kanjo is an independent open-source project published by Kyotu, not a product of Anthropic. "Claude" and "Claude Code" are Anthropic's names for its products.

## Assets

The **usage database** (`kanjo.db`) holds per-request usage numbers and metadata: project paths and names, git branches, session ids, the opaque account id of the session owner, the client names a user assigns to projects, budgets, alerts, and, only when the user turns it on, session titles. It holds no prompt or response text. [data-inventory.md](data-inventory.md) lists every field.

The **transcripts** under Claude Code's `projects` directory belong to Claude Code, not to Kanjo, but they contain the full conversations, and Kanjo can read them through the transcript viewer. Access to Kanjo's API with the viewer enabled therefore means access to conversation text.

The **credentials**: the database key (in the OS keyring or `kanjo.key`), the API access token (`access.token`), the session cookie derived from it, the single-use login codes, and, when TLS is configured, the TLS private key.

The **commands Kanjo controls**: the `statusLine` and hook entries in Claude Code's `settings.json`, the chained statusline command in `config.toml`, and the background service definition. Each of them is run by Claude Code or the operating system, so whoever can change them can run code as the user.

The **integrity of what Kanjo reports**: the price table that turns tokens into dollars, the binary itself, and the audit log.

## Trust boundaries

**Processes of the same user.** Kanjo trusts everything that runs as the same operating-system user. Such a process can read the transcripts directly, read the token and key files, ask the keyring for the key, edit `settings.json` and attach a debugger. Kanjo does not try to defend against it; see [Out of scope](#out-of-scope).

**Other local users.** Other accounts on the same machine are not trusted. They are kept out of Kanjo's files by file permissions and out of its API by the access token, but they can reach the loopback port, so the server must assume that every connection may come from one of them.

**The browser.** The dashboard runs in the user's browser, which also runs pages from anywhere on the internet. Those pages can make the browser send requests to `127.0.0.1`, so the server must refuse requests that a foreign page triggers and must not let a page read its responses.

**The network.** By default Kanjo listens on loopback only and makes no outbound connections. A user can choose to listen on another address, and then the network is untrusted.

## Threats, mitigations and residual risk

### From the browser

| Threat | Mitigation | Residual risk |
| --- | --- | --- |
| A web page sends a state-changing request to the local API (cross-site request forgery), for example a purge or turning on the transcript viewer. | `POST`, `PUT`, `PATCH` and `DELETE` need the header `X-Kanjo-CSRF: 1`, which a cross-origin page cannot set without a CORS preflight that Kanjo never answers. A foreign `Origin` header and `Sec-Fetch-Site: cross-site` or `same-site` on `/api` are refused. The session cookie is `SameSite=Strict`. (`security::guard`; test `requests_without_valid_credentials_or_from_elsewhere_are_refused`.) | Low. Relies on browsers implementing CORS, `Origin` and `SameSite` as specified. |
| DNS rebinding: a page on a domain that resolves to `127.0.0.1` reads API responses as same-origin. | The `Host` header must name this server: a loopback name, the configured bind address or the address the connection arrived on, with the listening port (`Inner::host_allowed`). Anything else gets `403`. | Low. |
| A page locks the owner out by making the browser fetch `/?token=wrong` many times. | A wrong login link counts towards the lockout only when the browser marks it as a navigation that did not come from another site; the right token, cookie or login code is always accepted, even during a lockout (`counts_against_peer`; test `wrong_login_links_from_other_sites_do_not_count`). | Low. A browser that sends no `Sec-Fetch-*` headers falls back to counting. |
| Script injection in the dashboard, for example through a project name, branch name or transcript text shown in the viewer. | The UI's Content-Security-Policy allows scripts only from the server itself and by the hash of the inline scripts in the embedded `index.html`, and styles from the server only; the API answers with `default-src 'none'` (`assets::policy_for`). Svelte renders text escaped, and `web/src/csp.test.ts` fails the build on `{@html}`, `innerHTML`, static `style` attributes and runtime `<style>` or `<script>` elements. | Low. A bug in the UI framework's escaping would still be contained by the CSP. |
| Framing the dashboard to trick the user into clicks (clickjacking). | `frame-ancestors 'none'` and `X-Frame-Options: DENY` on every response. | Negligible. |
| A login link redirects the browser to another site (open redirect). | After `/?token=` the server redirects only to a local path without `//`, `\` or `..` (`safe_path`; unit test `redirect_targets_stay_local`). | Negligible. |
| An exported CSV runs a formula when opened in a spreadsheet, through a branch name or title. | Text cells that start with `=`, `+`, `-` or `@` get a leading quote (`crates/kanjo-analytics/src/export.rs`). | Low. Applies to CSV only; JSON exports are data. |

### From other local users

| Threat | Mitigation | Residual risk |
| --- | --- | --- |
| Reading the database, key, token, spool or configuration files. | The data directory is created with mode 700 and every file with mode 600, the key and token files owner-only from the moment they exist (`create_private`). On Unix, `kanjo doctor` reports loose permissions on the data directory, the database, the key file, the token and `config.toml`. | On Windows Kanjo sets no access control list and relies on the permissions of the user profile. A user who has changed those, or who sets `--home` to a shared location, loses this protection. |
| Using the API on the loopback port. | Every `/api` request except `/api/v1/health` needs the access token or the session cookie. The token is 32 random bytes from the operating system, compared in constant time (`kanjo_ops::token::matches`). | With `auth = "none"` in `config.toml`, which is honoured only on loopback, every local user has full access to the API. That setting is meant for single-user machines. |
| Guessing the token. | Ten distinct wrong values within five minutes lock the peer out for five minutes; all of loopback counts as one peer, IPv6 counts per /64, and an overflow entry covers more than 4096 peers (`Limiter`; tests `limiter_counts_distinct_failures`, `the_overflow_bucket_is_enforced`). | Negligible against a 256-bit token. |
| Learning the token from a URL: command lines are readable by other users through `/proc` on Linux, and URLs end up in browser history. | `kanjo open`, `kanjo up` and the server's own browser start never put the token in a URL. They use a login code: 32 random bytes, valid once and for two minutes, accepted only by the server instance named in `server.json` (`server_file::login_url`, `claim_login_code`; test `login_codes_are_single_use_bound_to_the_instance_and_expire`). | The opener (`xdg-open`, `open`, `rundll32`) is not given the URL. It is given an owner-only local page in `open/`, named by a digest of the code, that forwards the browser to the sign-in URL and is removed once the code is used or after 20 seconds (`server_file::launch_page`). Until it is removed, the page holds a usable code and is protected by the same file permissions as `access.token`. A browser in a Snap or Flatpak sandbox may be unable to read a page in a hidden directory or in `/tmp`; then the code is not redeemed, `kanjo open` and `kanjo up` print the sign-in URL in the terminal after 20 seconds, and a server that opened the browser itself logs a warning. This fallback has not been tested against a real sandboxed browser. When no browser can be started, `kanjo open` prints the URL with the code in the terminal. |
| A program squats the configured port so that `kanjo open` hands it a credential, or serves a fake dashboard. | The command line only treats a server as Kanjo when `server.json` is held locked by a live process and its address answers, and the login code it sends is worthless to any other process (test `a_record_nobody_holds_is_stale`). | A squatter can still show a fake page to a browser that opens the port directly, for example from a bookmark. |
| Reading the session cookie through another loopback port. | The cookie is `HttpOnly` and `SameSite=Strict`, and its value is a SHA-256 derivative of the token, not the token. | Browsers scope cookies by host, not by port (RFC 6265, section 8.5). A program another user runs on the same loopback address receives the cookie if the user's browser opens it directly, and the cookie stays valid until the token file is replaced. There is no command to rotate the token and the cookie has no per-start component. |
| Filling all connection slots so the owner cannot connect. | At most 256 connections; when all are taken, the oldest connection that has not presented a valid credential is closed. Headers must arrive within 10 seconds, the TLS handshake within 10 seconds, request bodies are limited to 256 KiB and handlers to 30 seconds (300 for maintenance) (`net.rs`; test `idle_connections_cannot_keep_the_owner_out`). | Low. A local user can still use CPU and memory on the machine by other means. |
| Starting a second Kanjo server on the same data directory, or a demo that overwrites a real installation. | A server refuses to start while another holds `server.json`. `kanjo demo` ignores `KANJO_HOME`, uses a temporary directory unless `--home` is given, and refuses a directory that holds a real installation. | Negligible. |

### From the network

| Threat | Mitigation | Residual risk |
| --- | --- | --- |
| The dashboard is exposed on a LAN without protection. | The default bind is `127.0.0.1`. Any other address is refused unless `server.tls_cert`, `server.tls_key` and `auth = "token"` are all set; `auth = "none"` is ignored off loopback (`check_bind`, `auth_enabled`; test `non_loopback_binds_need_tls_and_token_auth`). | When a user does expose it, one shared token is the only credential. It grants everything the dashboard can do: all reports, settings, purge, backup, hook installation and, if enabled, the transcript viewer. There are no user accounts, no roles, no client certificates and no address allow-list. |
| Eavesdropping on an exposed dashboard. | TLS through rustls with the ring provider and its safe default protocol versions (TLS 1.2 and 1.3); the cookie gets `Secure` and responses get `Strict-Transport-Security` when TLS is on and the bind is not loopback (test `tls_is_served_with_rustls_and_the_cookie_is_secure`). A warning is logged if the TLS key file is readable by other users. | Certificate issuance, renewal and trust are the operator's job; Kanjo only loads PEM files. |
| Kanjo leaks data by connecting out (telemetry, update checks, price downloads, a dependency that phones home). | No HTTP, SMTP, DNS, telemetry or update client crate may enter the dependency tree, and the client features of `hyper` and `hyper-util` are banned (`deny.toml`). `scripts/egress-test.sh` runs `kanjo demo` under `strace` and fails on any `connect()` or `sendto()` to something other than loopback, a Unix socket or netlink, and in a network namespace that has only loopback. Notifications are local (D-Bus or the native notification centre). | The egress test exercises demo mode only, without the collector, the watcher or notifications. Its strace phase was run against a release build on Linux and passed; both phases run in the `egress` CI job on Linux, in strict mode, where a skipped phase fails. macOS and Windows have no egress test. |

### Data at rest and integrity

| Threat | Mitigation | Residual risk |
| --- | --- | --- |
| A copy of the database file (a stolen disk image, a synced folder, a backup that left the machine) is read. | SQLCipher 4 (4.20.0 as built, with the vendored OpenSSL 3 as its crypto provider): AES-256-CBC per 4096-byte page with an HMAC-SHA512 per page. Kanjo passes a random 256-bit raw key (`PRAGMA key = "x'...'"`), so SQLCipher uses it directly without passphrase derivation; the page HMAC key is derived from it with PBKDF2-HMAC-SHA512 and a per-database salt. Backups, pre-migration and pre-restore copies are encrypted with the same key. The key is in the OS keyring when one is available. (`crates/kanjo-core/src/store/mod.rs`; tests `opens_encrypted_and_rejects_wrong_key`, `backup_is_encrypted_with_the_same_key`.) | In key-file mode (and in `auto` mode without a usable keyring) the key sits next to the database in `kanjo.key`, so a copy of the whole data directory includes it. The spool is plain text. With `encryption = "off"` and in demo mode nothing is encrypted. The keyring protects the key only as far as the user's keyring does; most desktop keyrings release it to any process of the same user. |
| An existing database is made unreadable by a new key, for example when two processes start at once on a new machine. | Key lookup and creation run under an exclusive lock on `kanjo.key.lock`; a key is generated only when no key and no database exist, and an existing database without its key is an error, never a new key (tests `simultaneous_first_starts_agree_on_one_key`, `existing_database_without_key_is_an_error_and_no_key_is_made`). | Losing the key loses the data. Backing it up is the operator's job. |
| Deleted data survives: in free pages of the file, in the write-ahead log, or by being imported again from transcripts. | `secure_delete` is on, the log is truncated after purge and retention, and purge marks stop a rescan from bringing purged history back (tests `deleted_rows_do_not_linger_in_the_file`, `purged_text_is_gone_from_the_database_files`, `crates/kanjo-ingest/tests/purge.rs`). | Backups, the spool, exported files and logs are not touched by a purge, and restoring an older backup brings purged data back. See [data-inventory.md](data-inventory.md#deleting-data). |
| The audit log is altered to hide an export, a transcript view or a purge. | Each entry carries the SHA-256 of its fields and of the previous entry's hash, with length-prefixed fields; `kanjo audit verify` and every listing walk the chain (`crates/kanjo-ops/src/audit.rs`; test `tampering_is_detected`). In the API, a request whose audit entry cannot be written fails (for an export or a transcript view, before anything is returned); the command line warns and carries on. | The chain is not keyed and lives in the same database. Anyone who can write the database, which includes the user, can rewrite the log and recompute the chain. The actor's user name comes from `USER`, `LOGNAME` or `USERNAME`. Retention prunes entries older than 400 days by default and moves the anchor. The log shows accidental damage and edits by tools that do not recompute the chain; it is not evidence against the user who owns it. |
| A manipulated price table makes costs look lower or higher. | The table is compiled into the binary. An imported table must carry a minisign signature that verifies against a public key the user passes with `--pubkey`, unless `--allow-unsigned` is given, and the import is audited with whether it was signed (`crates/kanjo-ops/src/pricing.rs`). | There is no built-in signing key: the trust anchor is whatever key the user supplies. |
| A shared statusline payload or transcript record makes Kanjo store text it should not. | The parser decodes named fields only; unknown records are kept as type and top-level key names; titles are off by default and dropped before the spool; the statusline reader caps input at 16 MiB. | Fields that Kanjo does store, such as branch names and paths, can themselves contain sensitive words. Path redaction hides them in the UI and exports, not in the database. |

### Release and installation

| Threat | Mitigation | Residual risk |
| --- | --- | --- |
| A tampered release archive or installer. | Releases are built by `.github/workflows/release.yml` from the tag with `--locked` dependencies and pinned actions. `SHA256SUMS` lists every archive, SBOM and both installers and is signed keylessly with Sigstore cosign; the `sign` job runs the same `cosign verify-blob` the installers run right after signing, and the `package` job checks with `scripts/installer-repo-url.sh` that both installers pin this repository. Each archive, SBOM and installer gets a GitHub build provenance attestation; each binary embeds its dependency list (cargo-auditable). `install.sh` and `install.ps1` check the SHA-256, check the cosign signature against the exact workflow and tag when cosign is installed, stop on a failed check and print which checks ran. | The release workflow and its signing step have run once, for v0.1.0, and the cosign bundle has been verified only by the workflow itself, right after signing. Without cosign the installers rely on a checksum from the same download and say so in a warning. The installers' cosign 2 path has been tested only with stub commands. The minisign key has not been published. The signature identity is pinned to `https://github.com/Kyotu-Technology/kanjo`, so a fork has to change it in both installers. |
| A piped install (`curl ... \| sh`, `irm ... \| iex`) runs a script that was cut off in transit or that leaves the user's shell in a changed state. | `install.sh` keeps all of its work in a function called on the last line, inside braces, so a download cut off part way defines functions and exits without doing anything; it does not read standard input. `install.ps1` runs inside a script block of its own, leaves no variables, functions or preference settings in the caller's session, puts the TLS setting back, never calls `exit` and reports a failed check as an ordinary error; only `$env:PATH` changes, on purpose. `scripts/test-install.sh` pipes `install.sh` into `sh` and cuts it after every line and after every byte of the last line; `scripts/test-install.ps1` checks the session after `Invoke-Expression` and after the script block form. | The piped script itself is not verified before it runs: it is trusted as far as HTTPS to GitHub and the release asset are, and its own checks protect the archive it installs, not the script. A user who wants more downloads the installer first and checks it against `SHA256SUMS` and its cosign signature, or with `gh attestation verify`, before running it. The `releases/latest/download` URLs point to the latest release that is not a pre-release. The installers were run locally under dash, busybox sh, bash 3.2 and PowerShell 7.4 on Linux; on macOS and Windows they run only in the Installers CI job. |
| A vulnerable or malicious dependency. | `cargo-deny` checks advisories, licences, bans and sources, `scripts/cargo-audit.sh` audits `Cargo.lock` against a fresh RustSec database, and Dependabot proposes updates weekly for Cargo, npm and GitHub Actions. Only crates.io is an allowed source. | These are checks for known issues. They do not detect a malicious crate that has no advisory. |

## Out of scope

Kanjo does not defend against an attacker who has already compromised the user's account or runs malware as that user: such code can read the transcripts directly, read `access.token` and `kanjo.key`, ask the keyring for the database key, rewrite the audit log, edit `settings.json` or `config.toml` to run its own commands, or replace the binary. The same holds for an administrator or root user of the machine, for anyone with physical access to an unlocked session, and for a compromised browser or browser extension, which can act with the user's session. The security of Claude Code itself, of Anthropic's services and of the operating system's keyring is outside Kanjo. There is no team or company server, no user accounts or roles and no exchange of data between Kanjo installations, so this model does not cover them.

## Known gaps

These are open and recorded here so that nobody mistakes them for solved: a sandboxed browser (Snap or Flatpak) may be unable to open the local sign-in page, in which case the user has to open the printed sign-in URL by hand, and this has not been tested against a real sandboxed browser; there is no command to rotate the access token, and the session cookie is a fixed derivative of it; the session cookie is not isolated from other programs on another loopback port; the egress test has no macOS or Windows variant; the installers' signature checks have never run against a real release (the one real install, on Linux, had no cosign and skipped them), and the release signature has been verified only by the release workflow itself; the minisign public key is unpublished; the audit chain is unkeyed; file permissions on Windows are left to the profile's defaults.
