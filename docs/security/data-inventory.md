# Data inventory

This document lists every kind of data Kanjo stores or touches on the machine it runs on: what it is, where it comes from, whether it can identify a person or a client, how long it is kept by default, how it is protected and how it is deleted. It is written from the schema in `crates/kanjo-core/src/store/schema.sql`, the paths in `crates/kanjo-core/src/paths.rs` and the code that reads and writes them, and it is meant to be copied into an organisation's asset register (ISO/IEC 27001:2022 control A.5.9, see [iso27001.md](iso27001.md)).

Kanjo is an independent open-source project published by Kyotu Technology. It is not made, endorsed or supported by Anthropic. "Claude" and "Claude Code" are Anthropic's names for its products; Kanjo only reads files that Claude Code writes on the same computer.

## Where the data lives

Everything Kanjo writes is in one data directory per user, unless the user gives another one with `--home` or `KANJO_HOME`. The default is `$XDG_DATA_HOME/kanjo` (usually `~/.local/share/kanjo`) on Linux and the BSDs, `~/Library/Application Support/io.Kyotu.kanjo` on macOS and `%APPDATA%\Kyotu\kanjo\data` on Windows (`UserDirs::kanjo_data_dir`). On Unix the directory is created with mode 700 and every file in it with mode 600 (`create_private_dir`, `make_private_file`, `write_private_atomic`). On Windows Kanjo sets no access control list of its own; the files inherit the permissions of the user's profile directory. On Unix, `kanjo doctor` reports it when other users can read the data directory, the database, the key file, the token or `config.toml`.

The only places outside the data directory that Kanjo writes to are Claude Code's `settings.json` (with a backup beside it), the definition of the background service, the operating system's keyring and, through the browser, a cookie and one local-storage entry. They are listed in [Outside the data directory](#outside-the-data-directory).

What the logs contain: warnings and errors from the server and the collector, and at debug level an access log with method, path, status and duration. The access log never contains query strings (which can carry a sign-in code), headers, cookies or tokens (`security::access_log`). No log line contains prompt or response text.

## Tables in the database

The database is SQLite with SQLCipher encryption (see [threat-model.md](threat-model.md) for the parameters). All timestamps are epoch milliseconds in UTC. "Default retention" refers to the retention settings in `RetentionSettings` (`crates/kanjo-core/src/settings.rs`): request rows 400 days, hourly aggregates forever, limit readings 400 days, alerts 180 days, audit log 400 days, quarantine 90 days. A value of 0 keeps that class forever. Retention runs once a day in a running server and on `kanjo retention apply` (`kanjo_ops::retention::apply`).

| --- | --- | --- | --- | --- | --- |

| `request_tools` | Tool use per request: the tool block id, its kind (tool, MCP, skill, agent) and its name. For MCP tools only the server name is kept; for skills the skill name, for subagents the subagent type. No tool input. | Transcripts | MCP server and skill names can name an internal system or a client. | With its request | Yes |
| `sessions` | One row per session: id, project, title, git branch, Claude Code version, entry point, account id, first and last activity, totals. | Transcripts, statusline | Yes: `account` is the opaque account id Claude Code records for the session owner; `title` summarises the conversation. | Kept while the hourly aggregates are kept, which is forever by default | Yes |

No table stores prompt text, response text, thinking text, tool inputs or tool results. The parser in `crates/kanjo-ingest/src/record.rs` decodes only the fields listed in its `AssistantRecord`, `Usage` and `MetaRecord` structures and skips the rest without copying it.

### Session titles

A session title is the short summary Claude Code writes into the transcript (`ai-title` records) and sends as `session_name` in the statusline payload. Because it summarises what the conversation was about, Kanjo stores it only when "Store session titles" (`privacy.session_titles`) is on, and it is off by default. When it is off, the parser does not keep titles, the spool drain ignores them, and the statusline fast path drops `session_name` before it writes the spool line, controlled by `statusline.capture_titles` in `config.toml`, which the server keeps in step with the setting. Turning the setting off deletes the stored titles from `sessions` and `session_status` (`Ingestor::set_store_titles`).

### Spool

A statusline spool line carries: time, session id, session name (only with `capture_titles`), project directory, Claude Code version, model id and name, session cost, total and API duration, lines added and removed, context use and size, whether the context exceeds 200k tokens, fast mode, effort, the five-hour, seven-day and spend-limit readings, and the prompt cache state with miss causes (`StatuslineRecord` in `crates/kanjo-core/src/statusline.rs`). A hook line carries: time, event name, session id, working directory, source, model and agent type (`HookRecord` in `crates/kanjo-core/src/spool.rs`). The spool is the one place where data at rest is not encrypted even when the database is.

## Outside the data directory

**Claude Code's `settings.json`.** `kanjo up` (after asking) and the dashboard's "Connect Claude Code" add a `statusLine` command and `SessionStart`, `Stop` and `SessionEnd` hooks. A user's existing statusline command is moved to `config.toml` and run after Kanjo's (chain mode). Before every change Kanjo writes `settings.json.kanjo-backup-<UTC time>` next to the file, with the same permissions as the original, unless the newest backup already holds the same bytes (`crates/kanjo-setup/src/claude.rs`). These backups are full copies of the user's previous `settings.json`, which can hold anything the user put there, including environment variables. Kanjo never deletes them. `kanjo uninstall` removes Kanjo's entries and restores a chained statusline.

**The background service definition.** On Linux `~/.config/systemd/user/kanjo.service`, on macOS a LaunchAgent property list under `~/Library/LaunchAgents`, on Windows a launcher script under `%LOCALAPPDATA%\Kyotu\kanjo\service` and a value under `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`. They contain the path of the executable and of the data and Claude directories. `kanjo service uninstall` and `kanjo uninstall` remove them.

**The OS keyring.** In `auto` and `keyring` mode the database key is stored in Secret Service on Linux, the Keychain on macOS or Credential Manager on Windows, under the service name `kanjo` and the account `database-key:<data directory>` (`crates/kanjo-ops/src/keys.rs`). Kanjo never deletes this entry: `kanjo uninstall --purge-data` says so and asks the user to remove it with the keyring tool.

**The browser.** Signing in sets the cookie `kanjo_session` (`HttpOnly`, `SameSite=Strict`, `Path=/`, and `Secure` under TLS). Its value is a SHA-256 derivative of the access token, not the token. The UI keeps the chosen theme in local storage under `kanjo.theme`. Nothing else is stored by the page.

**Exported files.** `kanjo export` and the dashboard's export buttons write CSV or JSON files where the user chooses (by default the browser's download folder). These files are outside Kanjo's control: they are not encrypted, not covered by retention or purge, and carry whatever the export contains, with project names, paths, branches and clients replaced by aliases when path redaction is on.

## What Kanjo reads but never stores

Kanjo reads Claude Code's transcripts under `<Claude directory>/projects`, including subagent transcripts and their `meta.json`, and nothing else under that directory (`crates/kanjo-ingest/src/discover.rs`; symbolic links are not followed). From each line it decodes the record type and, for the record types it handles, the usage numbers and metadata listed above. The text of prompts, responses, thinking and tool calls passes through the JSON reader without being copied.

The transcript viewer, when the user has switched it on, reads one transcript on demand and returns 500 messages by default (user and assistant text, thinking text and tool names, each cut to 4000 characters) to the browser (`crates/kanjo-ingest/src/transcript.rs`). Nothing it reads is stored, and each view writes a `transcript.view` audit entry; if that entry cannot be written, the request fails and nothing is returned. The viewer is off by default.

The statusline and hook commands read the JSON Claude Code pipes to them. Fields not listed in [Spool](#spool) are dropped there.

To detect changes that break the prompt cache, Kanjo reads the user's `CLAUDE.md`, `settings.json` (and its `enabledPlugins`), and the `CLAUDE.md` in the working directory of each project active in the last seven days, hashes the content with SHA-256 and keeps only the size, modification time and hash (`crates/kanjo-ingest/src/config_files.rs`). The hash is not keyed, so for a very short or predictable file someone holding the database could confirm a guessed content.

`kanjo doctor` and the System page read the Claude directory's layout, `settings.json` (Kanjo's entries and `cleanupPeriodDays`) and the permissions of Kanjo's own files.

## Deleting data

Retention removes rows older than the configured ages, as listed above. Purge removes, on request, one project, one session, everything before a date, or everything (`kanjo purge`, or Delete data on the System page, both audited). After a purge Kanjo records a purge mark, so the purged history is not imported again by a rescan, a rewritten transcript or a restart; activity in the same session or project after the purge is recorded as usual (`crates/kanjo-ingest/tests/purge.rs`). The database runs with `secure_delete` on, so deleted rows are overwritten in the file, and the write-ahead log is truncated after a purge or retention pass (`deleted_rows_do_not_linger_in_the_file`, `purged_text_is_gone_from_the_database_files`).

A purge does not reach everything. It leaves the `projects` rows (path, name, client), `ingest_files` (transcript paths), budgets, settings and the audit log in place; the audit log keeps the record of the purge itself. It does not touch backups, pre-migration and pre-restore copies, the spool, exported files, logs or the `settings.json` backups. Restoring a backup made before a purge brings the purged data back, because the purge marks live in the database that is replaced. The transcripts themselves belong to Claude Code and are never changed or deleted by Kanjo.

`kanjo uninstall --purge-data` deletes the whole data directory with ordinary file deletion (no overwriting), after it has checked that no server is using it and that the directory looks like a Kanjo data directory. It leaves the keyring entry and the `settings.json` backups.

## Demo mode

`kanjo demo` writes invented data into a temporary directory, which it removes when it stops normally but leaves behind when it is killed (or into the directory given with `--home`, which it keeps), never reads the Claude directory and never touches the keyring or `settings.json`. Its database is deliberately unencrypted (`encryption = "off"` in its `config.toml`), because it holds only synthetic data. It refuses a directory that holds a real installation.
