# Feature status

This page says how far the current tree covers the functional specification Kanjo was built from. The specification is an internal working document in Polish; its feature names are given here in English with the Polish original in parentheses. It sorts features into MVP (one developer, offline), v1 (a company on its own network) and later. This release is the MVP.

Kanjo is an independent open-source project published by Kyotu, not a product of Anthropic. "Claude" and "Claude Code" are Anthropic's names for its products.

## How the statuses were set

The starting point was a coverage matrix written during an internal review, before the review's findings were fixed. Each row was then checked again against the code as it is now. Where a remark says something was run or checked, it was done for this document on Linux with a release build of `kanjo` made from the final tree of this release, in temporary directories with `KANJO_NO_KEYRING=1`: `kanjo demo` and its API, the reports (`daily`, `weekly`, `monthly`, `session`), `kanjo status` and `kanjo blocks --breakdown` on demo-seeded data, `kanjo open` with a stub browser opener, import and rescan of the synthetic transcript fixtures, `kanjo doctor`, backup, restore, purge, retention, `kanjo audit verify`, the statusline command and the egress test. Time zone handling across a daylight saving change was not run; it rests on the code and its tests. Nothing here was run on macOS or Windows, the background service and `kanjo up` were not run against a real service manager, the release workflow has not been executed, and the web UI was not rendered for this page, so what a remark says about the UI is read from its code.

"done" means the feature exists as the specification describes it for one developer; the remark gives limits that remain. "partial" means part of it is missing. "planned" marks a feature the specification puts after the MVP. Of the 56 MVP rows, 53 are done and 3 are partial; 5 rows are planned.

## Planned work beyond the table

The specification's roadmap describes the v1 release as a company server on the local network: a `kanjo` server mode that receives aggregates from developers' machines over mutual TLS, an OpenTelemetry receiver, single sign-on with roles, a project-to-client mapping with chargeback, team budgets, webhook and e-mail notifications, PDF reports, an audit log and encryption at rest on the server, and a Docker image. A later step adds more optimisation insights and a terminal UI. These are listed here as the roadmap states them; none of them exists in this release, and some parts that exist for one developer (client mapping, budgets, the audit log, encryption at rest) would need new work for a server. [architecture.md](architecture.md#a-team-server) says what in the current design is relevant to that.
